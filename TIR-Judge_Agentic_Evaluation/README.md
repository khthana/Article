สวัสดีครับเพื่อนๆ ที่ติดตามวงการ AI! วันนี้มาเรื่องที่แก้ปัญหาที่ใครที่เคยทดสอบ AI น่าจะเคยเจอ: "สั่งให้ AI เขียน 350 คำ ได้ 321 คำ แต่โมเดลยืนยันหน้าตายว่าครบ 392 คำแล้ว" จากงานวิจัยของทีม Google และ Emory University ที่เปิดตัว TIR-Judge (Tool-Integrated Reasoning Judge) — กรรมการ AI รุ่นใหม่ที่ไม่พึ่งพา "ความรู้สึกจากภาษา" แต่เขียนโค้ด Python รันใน Sandbox แล้วดูผลลัพธ์จริงแทนครับ

คุณเคยสังเกตไหมครับว่า ปัญหาที่น่ากลัวที่สุดของ AI ไม่ใช่การ "ไม่รู้" แต่คือการ "ไม่รู้ว่าตัวเองไม่รู้" — AI ที่ให้คำตอบผิดแต่มั่นใจ 100% เป็นอันตรายมากกว่า AI ที่บอกว่าไม่แน่ใจหลายเท่าครับ โดยเฉพาะเมื่อเราใช้ AI เป็น "กรรมการ" ตัดสิน AI ด้วยกันเองในระบบฝึกโมเดล?

คุณรู้ไหมครับว่า เมื่อเราให้ AI เป็นกรรมการตัดสินโมเดลอื่นๆ (LLM-as-a-judge) กรรมการตัวนั้นก็ยังต้องพึ่งพาการ "เดาตามความน่าจะเป็นของภาษา" แบบเดิม — ทำให้กรรมการเองก็ Hallucinate ได้เหมือนกัน เหมือนแต่งตั้งให้คนที่ตาไม่ดีไปทำหน้าที่ตัดสินการแข่งขันยิงธนู แล้วคาดหวังให้ตัดสินได้แม่นยำครับ?

และคุณเคยนึกไหมครับว่า ถ้าแทนที่จะให้กรรมการ "มองแล้วเดา" เราให้เขา "หยิบเครื่องมือขึ้นมาวัดจริงๆ" แทน — กรรมการคนเดิมที่เคยตาไม่ดีก็จะตัดสินได้แม่นขึ้นทันที เพียงเพราะมีไม้บรรทัดอยู่ในมือครับ?

งานวิจัยนี้กำลังบอกว่า: ปัญหาของ AI Judge ไม่ได้อยู่ที่ความฉลาดของโมเดล แต่อยู่ที่การขาด "เครื่องมือพิสูจน์ความจริง" — และ TIR-Judge ตอบโจทย์นี้ด้วยการให้กรรมการเขียนโค้ดตรวจสอบผลลัพธ์แทนการพึ่งพาภาษาอย่างเดียวครับ

========================================

🤔 ทบทวนความเชื่อเดิมๆ: สิ่งที่เราคิดเกี่ยวกับ AI Judge และ LLM Evaluation

▪ "การใช้ LLM ขนาดใหญ่เป็นกรรมการ (LLM-as-a-judge) คือมาตรฐานที่เชื่อถือได้ เพราะโมเดลที่ฉลาดย่อมตัดสินได้ถูกต้องกว่า" → กรรมการที่ฉลาดแต่ไม่มีเครื่องมือยังคง Hallucinate ครับ เพราะ Intrinsic Reasoning จากภาษาล้วนๆ ไม่สามารถ "พิสูจน์" ได้ว่าคำตอบถูกหรือผิด — มันแค่ "รู้สึกว่าน่าจะถูก" ซึ่งต่างกันคนละเรื่องกับการนับจริงหรือคำนวณจริงครับ

▪ "โมเดลที่มีพารามิเตอร์มากกว่าย่อมทำหน้าที่กรรมการได้ดีกว่า — ถ้าต้องการ Evaluation ที่แม่นยำต้องใช้โมเดลขนาดใหญ่" → TIR-Judge 8B เอาชนะ Reasoning Reward Model 32B บน PPE dataset ได้ถึง 6.4% (Pointwise) และ 7.7% (Pairwise) ครับ ขนาดไม่ใช่คำตอบถ้าเครื่องมือถูกต้อง

▪ "AI ที่ดีควรใช้เครื่องมือให้มากที่สุดเพื่อความแม่นยำ — เครื่องมือยิ่งเยอะยิ่งดี" → TIR-Judge ถูกฝึกให้ "ฉลาดในการเลือก" ผ่าน Format Reward ครับ — ถ้าใช้เครื่องมือกับงานง่ายเกินไปจะถูกหักคะแนน เพราะ Overhead ของ Code execution ในงานที่ตอบได้ด้วยภาษาล้วนๆ คือการสูญเสีย ไม่ใช่กำไรครับ

▪ "AI รุ่นเล็กที่เรียนจากการ Distillation จากโมเดลใหญ่จะดีกว่า AI รุ่นเล็กที่ฝึกจาก Scratch เสมอ — เพราะได้เรียนจากครูที่ฉลาดกว่า" → TIR-Judge-Zero (ฝึกด้วย RL ล้วนๆ ไม่มี Distillation) ที่ขนาด 4B สามารถเอาชนะรุ่นที่ผ่าน Distillation มาแล้วได้ 1.2% ครับ — บางครั้งการเรียนจากการ "ลองผิดลองถูกด้วยตัวเอง" ได้ผลดีกว่าการ "ลอกเพื่อน"

ความจริงที่น่าคิดคือ: AI ที่เก่งในการตัดสิน ไม่ใช่แค่ AI ที่รู้มาก แต่คือ AI ที่รู้ว่าตอนไหนควรหยิบเครื่องมือขึ้นมาพิสูจน์แทนการเดาครับ

=== ทำไม LLM-as-a-judge แบบเดิมถึงมีปัญหา? ===

เมื่อเราใช้ LLM ขนาดใหญ่เป็นกรรมการตัดสิน AI ตัวอื่น กรรมการนั้นต้องพึ่งพาสิ่งที่เรียกว่า Intrinsic Reasoning ครับ — นั่นคือการอ่านคำตอบแล้ว "ประมาณการ" ว่าถูกหรือผิด ดีหรือไม่ดี โดยอาศัยความน่าจะเป็นของภาษา

ปัญหาคือ Intrinsic Reasoning ไม่ได้ "รู้จริง" ครับ มันแค่ "น่าจะรู้" ตัวอย่างที่ชัดเจนที่สุด:

สถานการณ์จริง: ผู้ใช้ขอบทความ 350 คำ โมเดลส่งมา 321 คำ แล้วเขียนในตอนท้ายว่า "บทความนี้มีความยาวครบ 392 คำ"

กรรมการแบบ Intrinsic Reasoning: อ่านบทความ สังเกตว่ายาวพอสมควร ได้ยินโมเดลบอกว่า 392 คำ ก็อนุมานว่า "น่าจะถูก" แล้วตัดสินว่าผ่านครับ

กรรมการ TIR-Judge: เขียนโค้ด Python `len(response.split())` รันใน Sandbox ได้ผลลัพธ์ 321 ตัดสินว่า "ไม่ผ่าน" โดยไม่มีข้อโต้แย้งครับ

นี่คือช่องว่างระหว่าง "รู้สึกว่าถูก" กับ "พิสูจน์ว่าถูก" ที่ TIR-Judge ออกแบบมาเพื่อปิดครับ

=== Agentic Reasoning: เมื่อกรรมการทำตัวเป็น "นักสืบ" ===

สิ่งที่ทำให้ TIR-Judge แตกต่างจาก LLM Judge แบบเดิมคือการเปลี่ยน Mode การทำงานจาก Passive Reading เป็น Active Investigation ครับ

กรรมการแบบเดิม: อ่าน → คิด → ตัดสิน (ทั้งหมดอยู่ใน "หัว")

TIR-Judge: อ่าน → คิดว่าต้องตรวจสอบอะไร → เขียนโค้ด → รันใน Sandbox → อ่านผลลัพธ์จริง → ตัดสินตามหลักฐาน

เหมือนความต่างระหว่างผู้พิพากษาที่ตัดสินคดีโดยฟังปากคำพยานอย่างเดียว กับผู้พิพากษาที่สั่งให้ทีมสืบสวนไปเก็บหลักฐาน DNA มาก่อนแล้วค่อยตัดสินครับ คนแรกอาจถูก แต่คนหลังพิสูจน์ได้ครับ

=== Format Reward: ฝึกให้รู้จัก "ทำน้อยแต่ได้ผลมาก" ===

ประเด็นที่ซับซ้อนและน่าสนใจที่สุดอย่างหนึ่งใน TIR-Judge คือการออกแบบ Reward Function ที่เรียกว่า Format Reward (R_f) ครับ

ถ้าออกแบบ Reward ผิด โมเดลจะเรียนรู้ว่า "ใช้เครื่องมือทุกครั้ง = ดีเสมอ" แล้วเริ่มรันโค้ดกับทุกอย่าง รวมถึงงานที่ตอบได้ง่ายๆ ด้วยภาษา ซึ่งสร้าง Overhead โดยไม่จำเป็นครับ

Format Reward แก้ปัญหานี้ด้วยการ "ลงโทษ" การใช้เครื่องมือในงานที่ไม่จำเป็น เช่น:
— คำถามทั่วไปที่ตอบได้จากความรู้ (ไม่ต้องรันโค้ดเพื่อถามว่าเมืองหลวงฝรั่งเศสคือที่ไหน)
— งานด้านความปลอดภัย (Safety evaluation) ที่เน้นการตีความเจตนา ไม่ใช่การคำนวณ

และ "ให้รางวัล" การใช้เครื่องมือเฉพาะในงานที่จำเป็น เช่น:
— การตรวจสอบจำนวนคำ ตัวอักษร หรือรูปแบบที่กำหนด
— การพิสูจน์ตรรกะทางคณิตศาสตร์หรือโค้ดที่ซับซ้อน
— การ Verify ขั้นตอนการให้เหตุผลที่ตรวจสอบได้เชิงประจักษ์

ผลลัพธ์คือกรรมการที่ "ฉลาดพอที่จะรู้ว่าตอนไหนต้องหยิบเครื่องมือ" ไม่ใช่แค่กรรมการที่มีเครื่องมือแต่หยิบขึ้นมาทุกครั้งโดยไม่จำเป็นครับ

=== 8B ล้ม 32B: เมื่อวิธีการสำคัญกว่าขนาด ===

ผลการทดสอบบน PPE (Process-level Evaluation) dataset ที่เน้นความถูกต้องของตรรกะเชิงขั้นตอนครับ:

TIR-Judge 8B (Backbone: Qwen3-8B) vs Reasoning Reward Model 32B:
— Pointwise (ให้คะแนนคำตอบเดี่ยว): TIR-Judge ชนะ +6.4%
— Pairwise (เปรียบเทียบคำตอบ A vs B): TIR-Judge ชนะ +7.7%

บน RewardBench 2 การจัดอันดับแบบ Listwise:
— TIR-Judge ทำคะแนนได้ถึง 96% ของ Claude-Opus-4

สิ่งที่ทำให้ 8B ชนะ 32B ในบริบทนี้ไม่ใช่เพราะขนาดเล็กกว่าดีกว่า แต่เพราะ Tool Integration เปลี่ยนชนิดของงานที่โมเดลต้องทำครับ แทนที่จะต้อง "จำ" และ "ประมาณ" ความถูกต้องจากภาษา โมเดลแค่ต้อง "รู้ว่าต้องถามคำถามอะไร" แล้วปล่อยให้ Code executor ทำงานแทนครับ เหมือนนักสืบที่ไม่จำเป็นต้องแก้สมการในหัว แค่รู้ว่าต้องส่งหลักฐานไปให้ Lab ตรวจและอ่านรายงานผลครับ

=== TIR-Judge-Zero: เรียนรู้ด้วยการลองผิดลองถูก ไม่ใช่การลอกเพื่อน ===

การที่ TIR-Judge-Zero ไม่ผ่านการ Distillation จากโมเดลใหญ่ถือเป็น Design Choice ที่ Bold มากครับ เพราะ Conventional wisdom บอกว่าการสอนโมเดลเล็กให้เลียนแบบโมเดลใหญ่คือ Shortcut ที่ดีที่สุด

แต่ TIR-Judge-Zero พิสูจน์ว่า Shortcut บางครั้งก็มีขีดจำกัดอยู่ที่ "เพดานของต้นแบบ" ครับ ถ้าโมเดลใหญ่ที่ใช้เป็นครูยังมีจุดอ่อน โมเดลเล็กที่ Distill จากมันก็จะรับจุดอ่อนนั้นมาด้วย

กระบวนการ Iterative RL ของ TIR-Judge-Zero ทำงานอย่างไรครับ:

รอบที่ 1: โมเดลเขียนโค้ดไปตรวจสอบคำตอบ → โค้ดรันแล้ว Error → ได้รับ Error Message กลับมา

รอบที่ 2: โมเดลอ่าน Error อ่านบริบทอีกครั้ง แก้โค้ดแล้วรันใหม่ → ยังมีปัญหาบางส่วน

รอบที่ 3: โมเดลวิเคราะห์ปัญหา ปรับแนวทาง เขียนโค้ดใหม่ → รันสำเร็จ ได้ผลลัพธ์ที่ใช้ตัดสินได้

กระบวนการวนซ้ำนี้ทำให้โมเดลเรียนรู้ "วิธีคิดเกี่ยวกับการใช้เครื่องมือ" ไม่ใช่แค่ "ลอกวิธีที่ครูใช้" ครับ ผลคือ TIR-Judge-Zero ขนาด 4B ชนะรุ่น Distilled 4B ได้ 1.2% — ซึ่งฟังดูเล็กน้อยแต่ในโลก Benchmark ที่ต่างกันแค่หลักทศนิยมนั้นถือว่าสำคัญมากครับ

=== Pointwise, Pairwise, Listwise: กรรมการที่ยืดหยุ่นสำหรับโลกจริง ===

ในการพัฒนา AI จริงๆ ต้องการ Evaluation หลายรูปแบบตามบริบทที่ต่างกันครับ TIR-Judge รองรับทั้งสามครับ:

Pointwise Evaluation: ให้คะแนนคำตอบเดี่ยวว่าดีระดับไหน — ใช้เมื่อต้องการ Quality Filter เช่น กรองคำตอบที่แย่เกินเกณฑ์ออกก่อนนำไปใช้ครับ

Pairwise Evaluation: เปรียบเทียบคำตอบ A กับ B แล้วเลือกผู้ชนะ — นี่คือมาตรฐานที่ใช้ในการเทรน RLHF เพื่อสอนโมเดลให้รู้ว่าแบบไหนดีกว่าในสายตามนุษย์ครับ

Listwise Evaluation: จัดอันดับคำตอบหลายๆ ตัวพร้อมกัน — มีประโยชน์มากในการ Best-of-N Sampling ที่ต้องการเลือก "ดีที่สุด" จากหลายตัวเลือกครับ เหมือนกรรมการที่ต้องตัดสินผู้เข้าแข่งขัน 10 คนพร้อมกัน ไม่ใช่แค่ตัดสินว่าใครชนะในแมทช์เดี่ยวครับ

🎯 ประเด็นที่ควรคิดต่อ

TIR-Judge ไม่ใช่แค่เครื่องมือใหม่ แต่สะท้อน Design Philosophy ที่สำคัญมากสำหรับอนาคตของ AI Evaluation ครับ:

— "พิสูจน์ได้" สำคัญกว่า "น่าจะถูก": ในโลกที่ AI ถูกนำไปใช้ในงานที่สำคัญมากขึ้น เช่น กฎหมาย การแพทย์ วิศวกรรม การตัดสินที่ "น่าจะถูก" ไม่พอครับ ต้องการการตัดสินที่ "พิสูจน์ได้" — และ TIR-Judge เป็นก้าวสำคัญในทิศทางนั้นครับ
